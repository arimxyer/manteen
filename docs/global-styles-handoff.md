# Required global styles handoff

Status: **contract frozen; production implementation in progress.** The disposable framework probe
proved the proposed import arrangement. It did not exercise Manteen ownership, receipt migration,
drift handling or rollback; those are the acceptance boundary for admitting Carousel and Dropzone.

## Question and stopping condition

Can a registry item declare a package-level stylesheet such as
`@mantine/carousel/styles.css`, and can `manteen` install and maintain that requirement without
rewriting a consumer's host stylesheet or guessing at framework-specific PostCSS behavior?

This milestone stops when:

1. the kit compiles a compact import list through the existing shadcn-compatible `css` field;
2. the CLI accepts only the import-only subset and refuses every broader CSS shape;
3. `init` creates one explicitly configured, Manteen-owned stylesheet and wires it after Mantine
   Core styles but before the consumer's host stylesheet;
4. `add`, `diff` and `update` compose and maintain that file through receipt v2;
5. v1 receipts migrate in memory and are rewritten only by a successful mutation;
6. stylesheet drift is visible and participates in `--force`, preflight and journal rollback; and
7. the built Node CLI installs Carousel and Dropzone into disposable Vite, Next App, Next Pages,
   Next hybrid and React Router consumers, including the Tailwind coexistence probe.

## Evidence already produced

The disposable probe wrote this import-only managed stylesheet:

```css
@import "@mantine/carousel/styles.css";
@import "@mantine/dropzone/styles.css";
```

It was imported after `@mantine/core/styles.css` and before the generated app's own CSS. Vite, Next
App, Next Pages and React Router production builds and browser renders succeeded; removing the
managed import was the negative control and left the extension components unstyled. The probe used
only disposable projects under `/tmp`.

That is framework evidence for the import arrangement only. The stylesheet was written manually,
so it is not evidence for registry parsing, CLI composition, receipts, drift, rollback or update.

## Frozen authoring and wire contract

Authors use a compact list:

```json
{
  "css": ["@mantine/carousel/styles.css"]
}
```

The kit compiles it to the existing interchange field:

```json
{
  "css": {
    "@import \"@mantine/carousel/styles.css\"": {}
  }
}
```

This is intentionally a strict subset of shadcn's broader `css` surface. Every entry must be an
exact package import with an empty declaration object. Selectors, declarations, nested values,
relative imports, URLs, media imports and other at-rules refuse as `css-unsupported`; they are not
silently dropped. The imported package must also be declared in that same item's runtime
`dependencies`, otherwise `css-dependency-missing` refuses. A `devDependencies` entry does not make
runtime CSS available to the installed component.

## Project and ownership contract

`manteen.json` gains an explicit `styles` path. `init` chooses `<sourceRoot>/manteen.css` (`src` for
Vite and source-root Next, `app` for React Router, repository root for root-layout Next), creates a
canonical empty file and wires it after Mantine Core styles but before the host stylesheet. Manual
mode creates/configures the file and prints that same required ordering as an integration step.

The managed stylesheet is a composed artifact like the theme, not an ordinary registry file. Its
contents are deterministic imports derived from all installed item contributions. Manteen owns the
whole file. Consumer overrides belong in the host stylesheet imported after it; Manteen never edits
that host stylesheet. A CSS-bearing item in an older project with no configured managed stylesheet
refuses with a named instruction to run `manteen init`.

## Receipt v2

The successful mutation receipt records both the composed bytes and their provenance:

```json
{
  "lockfileVersion": 2,
  "styles": {
    "destination": "src/manteen.css",
    "sha256": "...",
    "sources": [
      {
        "itemId": "@house/carousel",
        "dependsOn": [],
        "imports": ["@mantine/carousel/styles.css"]
      }
    ]
  }
}
```

Sources are ordered dependency-first, then by canonical item id; imports preserve author order and
exact duplicates collapse at first occurrence. Updating an item replaces that item's contribution,
including removing it when the new item no longer declares CSS. Contributions from untouched items
remain. The final stylesheet hash covers the exact generated bytes.

The v1 schema stays frozen. Readers validate v1 against that schema, migrate a valid document in
memory to v2 with `styles: null`, and validate v2 against the current schema. Read-only commands do
not rewrite a v1 receipt. A successful `add` or `update` writes v2; failed, refused and cancelled
operations leave the original receipt byte-identical.

## Lifecycle and refusal contract

- Planning includes the managed stylesheet in dry-run output and verifies its receipt/config/hash
  state before mutation.
- `global-styles-unconfigured` and `global-styles-uninitialized` are non-forceable: the safe remedy
  is `manteen init`, not guessing a destination or adopting unknown bytes.
- `global-styles-drift` is forceable because the file is explicitly Manteen-owned. The diagnostic
  tells the user to move overrides into the host stylesheet; `--force` restores generated bytes.
- Apply writes files, theme, managed styles and then the receipt through one pre-image journal.
  Any failure restores all source artifacts; dependency installation remains outside the journal.
- `diff` reports local and upstream axes for managed styles just as it does for the composed theme.
  `update` continues to route through the ordinary plan/apply pipeline.

## Acceptance matrix

The contract is not complete until automated tests cover import parsing, missing runtime
dependencies, deterministic composition/dedupe, v1-to-v2 migration, an existing-project `init`
migration, malformed CSS, unconfigured/uninitialized state, stylesheet drift with and without
`--force`, no-op repeat installs, update removal/replacement, preflight races and rollback.

Built-Node disposable acceptance then covers all four adapters plus Next hybrid, and includes a
current Next + Tailwind project. The Tailwind probe must show that Manteen adds only a TS/TSX
side-effect import and its separate managed CSS file; it must leave the project's PostCSS ordering
untouched.
