# Manteen 0.8 release handoff

[Documentation map](../project-context.md) · [Release receipts](README.md)

Status: complete and public on 2026-08-10. The client package, hosted portability matrix, npm
provenance, fresh public consumer, isolated agent probe, follow-up registry guidance correction,
and Pages deployment are accepted. `manteen-kit@0.2.1` remains unchanged.

## Release boundary

PR [#26](https://github.com/arimxyer/manteen/pull/26) merged the client candidate at
`8baa206baa2eb8a55b3068e55e03d1160bebf36d`. The signed annotated tag `manteen-v0.8.0`
points to that merge commit and GitHub reports its SSH signature as verified.

The client-only release extends the agent-native foundation with:

- deterministic relevance ranking for queried list results, with machine-readable rank reasons;
- truthful init dry-run refusal reporting and bounded named Vite `App` export support;
- dependency subprocess isolation for machine JSON and narrow additive config completion;
- explicit separation between registry installation and application integration; and
- Agent Guide and LLM context updates that describe the complete behavior as `manteen@0.8.0`.

There is no kit tag or kit publication in this release.

## Isolated public agent acceptance

A separate temporary Vite React TypeScript application installed only public `manteen@0.8.0`.
Herdr launched a Codex agent in its own workspace with an isolated `CODEX_HOME`, isolated npm
cache, and no Manteen source checkout. The isolated home contained only the copied login
credential, and the prompt prohibited prior memories and global skills. It stated the desired
outcome but supplied no Manteen commands.

The agent independently:

1. discovered CLI help and the dry-run/`planDigest`/`--expect-plan` workflow;
2. initialized Vite noninteractively;
3. queried `card`, used the deterministic ranking and descriptions, and selected
   `@house/article-card`;
4. inspected the complete docs, props, Styles API, dependencies, and usage metadata;
5. installed the component and its license/dependency graph;
6. followed the post-install instruction that installation is not integration, edited
   consumer-owned application code, and rendered the component; and
7. obtained healthy `status`, clean receipt/upstream `diff`, and a successful production build.

The probe first described a plan-digest refusal as stale. A follow-up comparison proved the
contract was correct: the reviewed command used `--no-overwrite`, while the attempted apply used
`--yes`, which implies overwrite. The machine response refused before mutation with
`plan-mismatch`; the agent reclassified its own finding.

The probe did find one real guidance defect: the hosted Article Card usage imported
`@ui/article-card`, while init configures the consumer `@/*` alias. It corrected the import to
`@/components/ui/article-card` and built successfully.

## Hosted usage correction and Pages acceptance

PR [#27](https://github.com/arimxyer/manteen/pull/27) corrected all affected registry usage and
docs playground snippets, made the authoring workspace typecheck the same consumer imports, and
added a mechanical regression test. Its full hosted CI
[run 31421251686](https://github.com/arimxyer/manteen/actions/runs/31421251686) passed before merge
commit `a695c0052c2429adba79be540646b25b4ca19bc6`.

Because usage metadata is served by the registry rather than baked into the npm binary, no client
patch release was required. Manual Pages
[run 31421895691](https://github.com/arimxyer/manteen/actions/runs/31421895691) built and deployed
that exact merge commit. Cache-busted public checks then proved:

- the registry index contains 22 items;
- Article Card serves `import { ArticleCard } from "@/components/ui/article-card";`;
- the public Agent Guide, `llms.txt`, and `llms-full.txt` carry the 0.8 availability and
  install-versus-integration guidance; and
- the already-published `manteen@0.8.0 info @house/article-card --usage --json` command reads the
  corrected hosted import.

The tag/package receipt and the later registry/docs deployment remain intentionally distinct: the
package tag resolves to `8baa206`, while current Pages resolves to the guidance-only follow-up
`a695c00`.
