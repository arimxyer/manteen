## Release boundary

Version `0.3.0` is the client release for four related maintenance contracts:

1. receipt v3 stores distinct accepted-result and pristine-upstream hashes, with exact bases under
   `.manteen/bases/`;
2. ordinary source updates use those bases for conflict-free three-way merging, preserve local
   adaptations and reserve `--take-upstream` for an explicit destructive reset;
3. a successful state-changing apply emits `state-versioning-required`, naming
   `manteen.lock.json` and `.manteen/bases/` as one versioned unit without inspecting Git; and
4. configured project scripts can verify the applied result after the update transaction, with
   fail-fast execution and bounded managed/control-byte drift detection.

This is a client-only release. `manteen-kit` stays at public `0.2.0`, and the client keeps its
existing `manteen-kit@^0.2.0` dependency. No registry item, generated `/r` artifact or docs-site
deployment was part of the tagged release, so there was no kit tag or release-workflow Pages
dispatch. The separate post-release train subsequently deployed and accepted all 22 source items
from commit `8853a720352c8842ce6957a494f919ec7cccda67`.

## State-format break

Receipt v3 is the only accepted state format. Receipt v1 and v2 do not contain the pristine
ancestor bytes required for a truthful three-way merge, so `0.3.0` rejects them rather than
inventing an ancestor or silently resetting local source.

That is a deliberate pre-1.0 compatibility break. A project with `0.2.x` state cannot treat the
upgrade as an ordinary in-place update. It must either remain on `0.2.x` or explicitly adopt fresh
v3 state, with its current source backed up and the reset/re-adoption reviewed. There is no
automatic migration claim in this release. The design decision was made while the tool had no
active consumer projects to preserve; public package availability by itself is not evidence that
every possible external project is absent, so the published release notes must keep this warning.

Once v3 state exists, the receipt and `.manteen/bases/` must be committed together. Manteen emits
the state-versioning advisory only when a successful `add` or `update` changes that unit. The
advisory proves that this run changed versionable state; it does not prove Git is installed, the
paths are tracked or a future commit will include them.

## Highest-value post-release lifecycle follow-on

The next lifecycle milestone should be safe, explicit upstream pruning. Today a file removed by
the registry is reported and retained with its receipt/base record. That is conservative, but it
leaves obsolete source behind and there is still no `remove` command.

The follow-on should preview every pruning candidate, distinguish an unchanged installed file
from a locally adapted or locally missing one, require an explicit user selection or named
destructive operation, and journal project-file, base and receipt removal together. It must not
infer a rename from similar text or treat upstream absence as permission to delete local work.
That contract is intentionally not implemented or included in `0.3.0`.
