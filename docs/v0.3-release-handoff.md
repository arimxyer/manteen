# Version 0.3 release handoff

Status: **client-only release candidate prepared locally.** The manifest and changelog identify
`manteen@0.3.0`, but no release tag has been pushed, no hosted release workflow has run, and no
OIDC, npm, provenance or fresh public-consumer receipt exists for this version. The last recorded
public proof remains `manteen@0.2.0` until those boundaries close.

## Release boundary

Version `0.3.0` is the client release for four related maintenance contracts:

1. receipt v3 stores distinct accepted-result and pristine-upstream hashes, with exact bases under
   `.manteen/bases/`;
2. ordinary source updates use those bases for conflict-free three-way merging, preserve local
   adaptations and reserve `--take-upstream` for an explicit destructive reset;
3. a successful state-changing apply emits `state-versioning-required`, naming
   `manteen.lock.json` and `.manteen/bases/` as one versioned unit without inspecting Git; and
4. configured project scripts can verify the applied result after the update transaction, with
   fail-fast execution and bounded managed/control-byte drift detection.

This is a client-only candidate. `manteen-kit` stays at public `0.2.0`, and the client keeps its
existing `manteen-kit@^0.2.0` dependency. No registry item, generated `/r` artifact or docs-site
deployment is part of this release, so there is no kit tag and no Pages dispatch in this plan.
That is a scope exclusion, not a claim that the checkout has no pending registry or docs-site
changes: publishing those bytes is a separate release train that needs its own review and
receipts.

## State-format break

Receipt v3 is the only accepted state format. Receipt v1 and v2 do not contain the pristine
ancestor bytes required for a truthful three-way merge, so `0.3.0` rejects them rather than
inventing an ancestor or silently resetting local source.

That is a deliberate pre-1.0 compatibility break. A project with `0.2.x` state cannot treat the
upgrade as an ordinary in-place update. It must either remain on `0.2.x` or explicitly adopt fresh
v3 state, with its current source backed up and the reset/re-adoption reviewed. There is no
automatic migration claim in this release. The design decision was made while the tool had no
active consumer projects to preserve; public package availability by itself is not evidence that
every possible external project is absent, so the published release notes must keep this warning.

Once v3 state exists, the receipt and `.manteen/bases/` must be committed together. Manteen emits
the state-versioning advisory only when a successful `add` or `update` changes that unit. The
advisory proves that this run changed versionable state; it does not prove Git is installed, the
paths are tracked or a future commit will include them.

## Remaining fail-stop release sequence

The release stays incomplete until all of these happen in order:

1. Review and merge one exact candidate commit after the full hosted PR matrix passes, including
   built Node on Linux, macOS and Windows and the packed package-manager consumers. The Windows
   run must exercise the new project-script verification path rather than relying only on the
   earlier generic CLI matrix.
2. Before tagging, confirm that no client-tarball file changed after the public-kit compatibility
   receipt above. If one did, repeat that smoke against the exact merged package bytes; a
   workspace-packed kit is not an acceptable substitute.
3. Push `manteen-v0.3.0` at the reviewed merge commit. The existing trusted-publisher workflow,
   not a local npm session, must rerun the guards, builds and full built-Node tier and perform
   `npm publish --provenance --access public`.
4. Record the exact commit, tag, GitHub release-run URL and conclusion. Independently record npm's
   published version/time, dist-tag, SHA-1, integrity and SLSA provenance for `manteen@0.3.0`.
5. In a fresh directory outside this checkout, install `manteen@0.3.0` from public npm and consume
   the public HTTPS registry. Confirm discovery/add, the state-versioning advisory, configured
   verification, the consumer's typecheck/build and the resulting v3 receipt/base shape. Record
   this as public npm-plus-HTTPS distribution proof only.
6. Separately exercise the update state machine against a controlled registry with named old and
   new revisions. Prove a local-only adaptation plus an upstream-only change, conflict refusal,
   explicit `--take-upstream`, and verification success and failure. A fresh install against one
   static public registry revision cannot manufacture those transitions and must not be presented
   as proving them.

A red hosted job stops before tagging. A tag or workflow log is not an npm receipt, and an npm
receipt is not a public-consumer receipt. Until steps 1–6 are recorded, this document must retain
its release-candidate status and `manteen@0.2.0` remains the last recorded publicly proven client
line.

## Highest-value post-release lifecycle follow-on

The next lifecycle milestone should be safe, explicit upstream pruning. Today a file removed by
the registry is reported and retained with its receipt/base record. That is conservative, but it
leaves obsolete source behind and there is still no `remove` command.

The follow-on should preview every pruning candidate, distinguish an unchanged installed file
from a locally adapted or locally missing one, require an explicit user selection or named
destructive operation, and journal project-file, base and receipt removal together. It must not
infer a rename from similar text or treat upstream absence as permission to delete local work.
That contract is intentionally not implemented or included in `0.3.0`.
