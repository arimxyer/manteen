# Version 0.4 release handoff

Status: **release candidate locally accepted; hosted release-candidate acceptance remains open.**
The implementation is merged and its feature PR was hosted-green; no `manteen-v0.4.0` tag or
public `manteen@0.4.0` package is claimed yet.

## Release boundary

`0.4.0` is a client-only lifecycle release for explicit pruning of ordinary receipt-owned files
that their same current registry item no longer publishes. It adds only
`manteen remove --upstream-removed` with unselected discovery, exact repeated `--file` selection,
and the additional `--discard-adapted` intent required before deleting locally adapted source.

The command resolves every receipt item plus its current transitive dependency closure before it
grants deletion authority, never infers a rename, and journals the selected source, pristine base,
and receipt together. Its exact contract and evidence boundary are in
[`upstream-removal-handoff.md`](upstream-removal-handoff.md).

This release does not change `manteen-kit@0.2.0`, the client dependency on `manteen-kit@^0.2.0`,
receipt version 3, registry wire/schema behavior, update merging, verification, registry content,
or the Pages deployment. It creates no kit tag and requires no Pages dispatch.

## Candidate and publication sequence

1. Bump only `manteen` and the workspace lock entry to `0.4.0`; keep the kit at `0.2.0`.
2. Move the removal changelog under `0.4.0`, update the packed README/public CLI documentation,
   and pass the tag-specific release guard plus the complete local suite.
3. Merge one release-candidate PR after its required hosted matrix passes.
4. Create and push the signed `manteen-v0.4.0` tag at that exact merge commit.
5. Require the credential-free tagged release workflow to pass before reading npm as evidence.
6. Verify npm metadata, tarball integrity and SLSA provenance independently.
7. Install exact public `manteen@0.4.0` in a fresh disposable consumer and exercise unchanged and
   adapted upstream-removal transactions against controlled old/current registry revisions.

The public receipt will record the exact merge, tag, workflow, npm integrity/provenance and fresh
consumer facts only after they exist. A packed candidate, green PR or pushed tag is not
publication evidence.

## Post-release follow-on

After public acceptance, the next milestone is an evidence-only AST-assisted merge-classification
spike. It may compare conservative structural classification with the released line-oriented
diff3 baseline, but it cannot change `update`, `diff`, emit AST-printed bytes, or claim a conflict
rate from synthetic consumer adaptations. Any production integration requires a separately frozen
decision.
